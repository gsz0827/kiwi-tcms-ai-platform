# Allure 自动化执行报告

Web 与接口自动化每次新建执行记录时，自动创建独立报告任务。报告 worker 等待执行结束，再调用固定版本 Allure Report 3.20.0 生成单文件报告；不在页面请求或测试执行进程中生成。

## 查看

- Web 自动化测试 → 执行任务 → 任务详情 → 查看 Allure 报告。
- 接口自动化测试 → 执行任务 → 结果详情 → 查看 Allure 报告。
- 报告支持通过率、结果分类、用例分组、操作/断言步骤、Web 失败截图，以及私有 HTML 下载。
- 已有历史任务不会自动批量生成；任务结束且快照完整时，可在任务详情点击“生成 Allure 报告”。
- 报告失败可单独重试，不会重新执行浏览器操作或接口请求。取消、中断和未执行项映射为跳过，不算通过；接口请求异常映射为 broken，与业务断言失败分开。

## 执行详情与原始诊断

Web 与接口任务详情使用统一结果表，展示用例名称、结果和耗时；原始诊断默认折叠，点击对应行可查看，支持键盘操作。Web 保留步骤和失败截图入口；接口保留脱敏请求、响应摘要、断言期望/实际值及回写状态。Allure 是主要详细报告入口，但不替代这些原始诊断数据；生成失败时仍可查看原结果。

概览区保留执行进度、时间、取消、重跑及正式归档入口。未执行项不计为通过或失败；只读账号不显示修改执行/归档操作。页面仅重新组织展示，不修改历史快照、结果或已生成报告。

## 不等于正式结论

调试执行也有 Allure 报告。报告只描述本次自动化的实际结果，不自动归档正式测试报告、不自动验证/关闭缺陷，也不作为发布批准。正式结果仍使用已有人工确认、归档和审批流程。

每个执行记录唯一关联一个报告，生成后保存压缩 HTML 与 SHA-256 校验值；重跑产生新的执行记录和报告，旧报告不会被覆盖。当前不聚合跨任务 Allure 趋势/历史曲线，不将缺失的历史数据展示为真实趋势。

## 数据与安全

- 原执行快照与结果是报告唯一来源，不读取后来编辑的自动化配置。Web 最多 20 个结果；接口支持 20 条配置 × 10 组数据。
- 不导出请求头、请求体、响应正文、变量、定位器、操作输入或断言 expected/actual 值。仅保留用例名称、动作/断言标签、状态、HTTP 状态码、耗时、数据组和任务编号。
- Web 失败截图可能含页面敏感信息，只对任务所属账号开放；单图 2 MiB，总附件 6 MiB，超限项仍可从原执行页面查看。
- 所有报告页面、状态、生成和下载接口按源任务 owner 校验；其他账号（包括超级管理员）不可越权读取。只读角色可以读取自己的报告，但不能补生成或重试；生成接口要求 POST/CSRF。
- HTML 以 opaque sandbox 显示，不含 allow-same-origin，无法读取平台 Cookie/DOM。脚本、样式和附件只允许内联或 data/blob，禁止对外网络请求；移除固定版本模板的 Google Analytics 代码，下载文件也不包含此代码。
- Allure 的界面偏好使用 iframe 内临时内存，不访问平台浏览器存储。报告整页可下载后离线打开；下载文件包含本人的失败截图，分享前自行核对。
- CLI 单次限时 120 秒，HTML 64 MiB、压缩保存 12 MiB，worker 内存 768 MiB、CPU 1 核；超过上限会报错，不发布半成品。仅报告任务可重试，已有测试结果不变。
- 报告任务随源执行记录或所属账号删除；若需审计保留，应先下载/备份。暂不自动清理历史报告。
- 旧 Web 执行器仅记录用例总耗时，不记录单步骤耗时；Allure 单步骤耗时可显示 unknown，不能当作状态失败。接口各断言也不单独计时。

## 标准部署

`docker-compose.ai.yml` 包含 `allure-worker`，通过 `Dockerfile.ai` 的独立 target 构建。执行 `docker compose -f docker-compose.ai.yml up --build -d` 时一起启动；Web 扩展仍使用 `docker-compose.web.yml`。不需要在用户电脑上另装 Java、Node 或 Allure CLI。

当前 WSL 开发环境使用 `Dockerfile.allure-worker`、镜像 `kiwi-allure-worker:local`、服务 `kiwi_allure_worker` / 容器 `kiwi_dev_allure_worker`；源代码及数据库沿用开发环境，不新增对外端口。新增迁移为 `allure_reporting.0001_initial`。

Nginx 的私有 artifact location 应保留 Django 提供的完整 CSP，避免叠加全局 script-only CSP。仓库的 `etc/nginx.conf` 和 `deployment/nginx.conf` 均包含对应局部规则；不放宽站点其余页面。

## 维护

- CLI 版本更新需要重新检查离线模板、隐私脚本移除规则、CSP、iframe 页面和下载内容，再更新镜像及固定版本记录。
- 检查 `allure_worker` 进程健康和报告 queued/generating/error 状态；5 分钟未更新的生成任务会重新排队，连续 3 次中断后转为错误。
- 数据库备份包含生成好的报告，压缩数据可能增大备份体积。数据库 `max_allowed_packet` 应至少 16 MiB。
- 禁用自动排队可在 Django 设置中设 `ALLURE_ENABLED=False`；历史补生成需任务详情显式确认，部署仍须报告 worker。
