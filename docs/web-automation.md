# Web 自动化测试

业务测试设计保存在用例库，Web 配置维护浏览器操作和断言。自动化配置按账号隔离，已关联配置继承业务用例的项目共享目录，不另外维护一套目录。AI 只生成可编辑草稿，逐条复核后保存，不自动执行。

## 正式执行

1. 从业务用例详情添加 Web 配置，或编辑已有配置关联同项目、可访问的业务用例。
2. 将业务用例加入测试计划，把对应 Web 配置组合成套件。
3. 创建当前账号的测试环境，设置允许访问的站点、环境变量和可选公共登录配置。
4. 套件点击执行，选择“正式执行”、测试计划、同版本构建和执行环境。缺失关联、不可访问用例、计划范围不符和跨项目环境会被拦截。
5. 提交前创建计划下的原生执行任务，每组数据对应独立执行实例，冻结业务用例内容版本、操作步骤、环境变量和构建归属。
6. 浏览器在后台执行；进入详情查看进度、结果及失败截图。结束后独立生成 Allure 执行报告，可从任务详情查看或下载 HTML，不代替正式归档与审批。计划详情的执行任务中有 Web 来源链接。
7. 执行结束后选择“确认结果 / 归档报告”，计划、构建和目标任务固定为提交时选择。仍需确认状态映射、共享摘要以及要创建缺陷草稿的失败项；不能覆盖已被人工修改的执行结果。
8. 归档产生报告不可变快照，后续审批、导出、质量门禁、缺陷关联和平台回归功能保持原有人工确认机制。

提交时只创建待执行记录，不自动将浏览器结果作为正式结论；取消、环境异常或未执行项不能计为通过。改变原任务的计划/构建、用例实例或执行结果后，归档安全校验会拒绝回写。

## 调试与历史

- 调试执行可以不关联业务用例，可使用套件站点或选择环境；不创建计划下的正式任务，不允许归档到正式报告。
- “原快照重跑（调试）”原样复用历史步骤和数据，创建新记录，不重写原任务；它不等于修复后回归。
- 自动化配置列表或编辑页可进入单配置调试，选择本人同项目的环境后确认执行。仅运行已保存配置，冻结环境和公共登录前置步骤，不为调试创建临时套件或正式任务。
- 执行详情中的‘失败项重跑（调试）’仅选择已经取得失败结果的项，保留原数据组和公共登录步骤；未执行项不会被当作失败项。产生独立记录，保留来源和原位置，不覆盖原报告。存在跨配置依赖时应完整重跑。
- 已归档的 Web 正式失败项可从缺陷发起独立的正式回归，详见下文；调试重跑仍不能验证缺陷。
- 旧运行被标记为“历史执行”，不补写计划或业务关联。缺少业务身份的旧快照不能事后追认；关联后需重新执行。已可归档的旧关联快照仍保留既有归档路径。

## 操作与断言编辑

配置和 AI 草稿复核共用表格步骤编辑器，可新增、复制、删除和调整顺序，并按操作类型显示定位器及输入/预期值。高级用户可以切换 JSON；格式或结构不兼容时保留原文本，不静默改写。服务器仍执行全部校验，禁用脚本和未支持的字段。

断言支持可见、隐藏、可用、包含文本、文本全等、输入值、元素数量、网址和标题。元素数量支持 0–10000 的整数文本或变量，运行前按数据组展开后校验。文本全等和输入值允许空字符串；所有断言使用 Playwright 自动等待机制，不仅检查操作完成。

## 视图与显示

套件、环境和执行列表跟随项目视图，也支持显式“全部项目”；分页保留查询条件。执行列表支持名称、发布版本、状态和提交日期筛选。版本只筛选已有正式版本归属的运行，不把无版本调试记录猜测归入某个版本。套件、环境是可复用项目资产，不假装属于单一发布版本。

Web 配置、套件、运行及 AI 历史日期按账号显示时区展示，数据库时间不改写。环境优先于兼容的套件站点/证书字段，执行确认和历史详情显示实际生效/冻结的站点。

## 边界与安全

- 浏览器为 Playwright Chromium；不接受任意 Python/JavaScript。
- 单配置 1–30 步且至少一个断言；数据组数 × 配置数最多 20，单步默认最长 10 秒，整轮约 5 分钟。这些保护本阶段不放开。
- 仅访问 `WEB_TEST_ALLOWED_ORIGINS` 显式允许的测试站点；浏览器服务还需要部署层网络隔离。
- 步骤值、环境变量、数据组和运行快照加密；输入值不写入步骤日志。失败截图可能包含页面敏感信息，仅任务所有者可访问。
- 公共登录每组执行一次，仅在本轮复用 Cookie/localStorage；不跨账号、任务或数据组复用。
- 所有写入均禁止只读账号；正式执行还要求计划权限、创建任务/执行记录和回写执行结果权限。
- 不重复创建业务用例，不迁移或删除旧配置、旧快照和历史报告。

## 部署与验证

先备份源码与数据库，应用 `web_testing.0006_formal_execution`，更新静态资源并重启 Web 服务与 Web worker。其他 AI/API worker本阶段无需更改。

相关测试包括 `tcms.web_testing.test_workflow`、Web 模块原测试、执行链和计划层级测试。实际浏览器验收使用临时测试项目、账号、计划、配置和环境，验证正式提交/归档与调试区别，结束后仅清理本次验收记录。

## 缺陷驱动的 Web 正式回归

已归档的 Web 正式失败项可在缺陷详情选择“新建 Web 回归”。缺陷须为“已修复”或“待验证”，选择同项目测试计划及与计划版本一致的修复构建；构建不能与原失败任务相同，用例须已纳入计划并已正式评审。

本次仅执行该缺陷对应的原失败项，复用当时加密保存的步骤、数据组、公共登录前置步骤、站点及证书策略，而非读取当前配置。须先将修复部署到原测试站点；需要更换站点或重设计步骤时，应重新进行正常正式执行，不能将调试冒充原失败项回归。

提交创建新的原生待执行任务及回归关联，保留原业务用例内容版本和执行属性，并将所选构建版本记录为缺陷修复版本。原执行与原报告不改写。原参数不会出现在回归确认页面或报告摘要中。

执行结束后先“确认结果 / 归档报告”，再在 Web 执行详情“确认缺陷回归结论”。归档或原始浏览器通过都不会自动关闭缺陷；确认通过转为待验证，需人工填写原因关闭；失败重新打开为处理中；取消、环境异常及未完成结果不计通过。重复提交或重复确认不会增加任务、验证记录或同状态审计记录，重复确认通过也不会重新打开已关闭缺陷。

验证会检查任务绑定、归档证据、缺陷身份、修复版本及原生状态；来自其他缺陷、普通正式任务或调试的结果不能作为此入口的回归证据。既有手工回归入口仍保留。
